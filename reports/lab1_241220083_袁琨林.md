## 二、实现思路

### 1. t1：LRU 替换器

Replacer 回答的是「没有空闲帧时淘汰谁」。LRU 用「双向链表 + 哈希表」：链表按最近一次访问排序，表头最久未用、表尾最近使用；哈希表把帧号映射到链表迭代器，定位与摘除都是 O(1)。链表元素是 `(帧号, 是否可淘汰)`，因此链表里同时存在被 pin 住的帧，`Victim` 必须从表头向后扫第一个可淘汰节点，不能直接取 `front()`。

两个语义关键点：`Pin` 既表示「帧被占用」也表示「刚刚访问过」，已有帧要 `splice` 到表尾；`Unpin` 只是解除占用、不算访问，所以只翻标志、不移动位置。`cur_size_` 只在可淘汰性变化时增减——新建节点、重复 Unpin 都不动它。

```c++
void LRUReplacer::Pin(frame_id_t frame_id) {
  std::lock_guard<std::mutex> lock(latch_);
  auto it = lru_hash_.find(frame_id);
  if (it == lru_hash_.end()) {                 // 首次访问：登记为不可淘汰
    lru_list_.emplace_back(frame_id, false);
    lru_hash_.emplace(frame_id, std::prev(lru_list_.end()));
    return;
  }
  if (it->second->second) {                    // 可淘汰 -> 不可淘汰
    it->second->second = false;
    --cur_size_;
  }
  lru_list_.splice(lru_list_.end(), lru_list_, it->second);  // 刷新最近访问
}
```

### 2. t2：缓冲池管理器

缓冲池由四部分组成：帧数组 `frames_`、页表 `page_frame_lookup_`、空闲帧链表 `free_list_`、替换器 `replacer_`。必须保证一条不变式：**同一帧不能同时出现在 `free_list_` 与替换器的可淘汰集合中**，否则会被两个请求重复分配。所以 `DeletePage` 把帧还给 `free_list_` 之前，要先把它从替换器里摘掉。

`FetchPage` 分两条路径：命中时只做 `frame.Pin()` 与 `replacer_->Pin()`，不产生磁盘 I/O；未命中时由 `GetAvailableFrame` 取帧（先 `free_list_`，再问替换器，都没有则抛 `NJUDB_NO_FREE_FRAME`），交给 `UpdateFrame` 装载。`UpdateFrame` 的顺序不能颠倒：

```c++
void BufferPoolManager::UpdateFrame(frame_id_t frame_id, file_id_t fid, page_id_t pid) {
  auto &frame = frames_[frame_id];
  auto *page  = frame.GetPage();
  const auto old_fid = page->GetFileId();
  const auto old_pid = page->GetPageId();
  if (frame.IsDirty()) FlushFrameLocked(frame_id);          // 1. 先写回，避免丢数据
  if (old_fid != INVALID_FILE_ID) page_frame_lookup_.erase({old_fid, old_pid});
  page->SetFilePageId(fid, pid);
  disk_manager_->ReadPage(fid, pid, page->GetData());       // 2. 装入新页
  frame.Pin(); replacer_->Pin(frame_id);                    // 3. 钉住
  page_frame_lookup_[{fid, pid}] = frame_id;                // 4. 登记映射
}
```

脏位设计成「粘性」的：`UnpinPage` 只在 `is_dirty` 为 true 时置位，永不因一次 false 调用而清除，否则「先按脏页解 pin、再被读路径解 pin 一次」就会把改动丢掉。多线程下整个缓冲池由 `latch_` 保护，拿不到帧的线程收到 `NO_FREE_FRAME` 后重试。

### 3. t3：表句柄

表文件分三层：第 0 页固定是表头（页数、首个空闲页、记录数、记录长度、每页槽数等），第 1 页起是数据页；数据页内是 `[页头 | 槽位图 | 槽位区]`，槽位区按定长记录存放，记录偏移 = 槽号 × `(tuple_header_size + rec_size)`。RID 由 `(页号, 槽号)` 组成，一次乘加即可定位。

表头的 `first_free_page_` 把「至少有一个空槽」的页串成链表，有三条必须维持的规则：新页创建即入链；页写满后移出；满页被删出空槽后重新入链。链表节点可能因并发或异常失效，`CreatePageHandle` 发现链头页其实已满时会顺手修复链表并继续找下一页。

四个 CRUD 都遵循「取页 → 校验 → 修改 → 按需维护链表与计数 → 解 pin（写操作标脏）」的骨架，异常路径先解 pin 再抛出，避免漏 pin 耗尽缓冲池。删除时先读出旧元组再清位，因为旧值既要进日志也要进事务写集合；「是否满页」的判定也必须在清位之前取。

```c++
void TableHandle::DeleteRecord(const RID &rid, Transaction *txn) {
  auto pg_hdl = FetchPageHandle(rid.PageID());
  if (!BitMap::GetBit(pg_hdl->GetBitmap(), rid.SlotID())) {   // 槽为空
    buffer_pool_manager_->UnpinPage(table_id_, rid.PageID(), false);
    NJUDB_THROW(NJUDB_RECORD_MISS, rid.ToString());
  }
  std::vector<char> image(tab_hdr_.nullmap_size_ + tab_hdr_.rec_size_);
  if (txn) pg_hdl->ReadSlot(rid.SlotID(), image.data(), image.data() + tab_hdr_.nullmap_size_);
  bool was_full = (page->GetRecordNum() == tab_hdr_.rec_per_page_);
  BitMap::SetBit(pg_hdl->GetBitmap(), rid.SlotID(), false);
  page->SetRecordNum(page->GetRecordNum() - 1);
  --tab_hdr_.rec_num_;
  if (was_full) AddPageToFreeListIfMissing(rid.PageID(), page);
  buffer_pool_manager_->UnpinPage(table_id_, rid.PageID(), true);
}
```

写路径还要做两件事：按 `[nullmap][记录数据]` 的物理镜像调用 `LogPageModification`（与恢复阶段 `ApplyRecoveryOperation` 的 redo 镜像一致），并往事务写集合追加 `TableWriteRecord`（旧元组 + LSN）供回滚使用。

### 4. f1：LRU-K 替换器

LRU-K 用「倒数第 K 次访问」判断冷热：对帧 e，记当前访问序号 `i_c`、倒数第 K 次出现的下标 `backward_K`，距离 `d_K = i_c − backward_K`；不足 K 次的帧距离记为 +∞。淘汰取 `d_K` 最大者，因此不足 K 次的帧总是优先被淘汰；若多个帧都是 +∞，按「首次访问时间最早」决定先后，策略在冷启动阶段退化为 FIFO。

返回类型用 `unsigned long long`，是为了让 +∞ 有可表示且必然大于任何真实距离的值。每节点只保留最近 K 个时间戳（环形覆盖），比较与摘除在同一把锁内完成。

### 5. f2：PAX 页句柄

PAX 与 NAry 的页头、槽位图完全相同，差别只在槽位区：先把所有 tuple header 连续排在最前，再按列存放，每列存 `rec_per_page_` 个定长值。nullmap 藏在 tuple header 里，所以 PAX 不需要单独的 nullmap 区。列偏移在 `TableHandle` 构造时算好放入 `field_offset_`：

```c++
size_t offset = tab_hdr_.rec_per_page_ * tab_hdr_.tuple_header_size_;
for (size_t i = 0; i < schema_->GetFieldCount(); ++i) {
  field_offset_.push_back(offset);
  offset += tab_hdr_.rec_per_page_ * schema_->GetFieldAt(i).field_.field_size_;
}
```

写一行时按字段「散射」到各列，读一行时再「聚集」回打包格式，因此上层 CRUD 完全不用改。`ReadChunk` 只沿列方向扫一遍连续内存即可得到整列 `ArrayValue`，这正是列存的收益；注意 nullmap 的位下标要用「字段在表 schema 中的序号」，而不是请求的 chunk 里的序号。

## 四、实验问题

### 问题一：沿一次页面读取（或写回）说明 page、frame、pin count 与 dirty flag 的变化；漏掉 Unpin 或脏位传错会看到什么？

以「命中后读取」为例。`FetchPage(fid, pid)` 先在 `page_frame_lookup_` 里查到 `fid_pid_t`，拿到 `frame_id` 后执行 `frame.Pin()`（pin_count 由 0 变 1），再调用 `replacer_->Pin(frame_id)`，该帧被标记为不可淘汰并移到 LRU 链表尾部。此时 page 的 `fid_/pid_` 与数据都已在内存中，不产生磁盘 I/O，dirty 保持原值。读操作结束后 `UnpinPage(fid, pid, false)`：pin_count 由 1 变 0，因为不再被使用，随即 `replacer_->Unpin(frame_id)` 把帧标记为可淘汰，dirty 仍为 false。

若是写回路径，`UnpinPage` 传入 true：`frame.SetDirty(true)` 把 dirty 置位，同时把 `rec_lsn_` 记为页面当前 LSN（文件头页除外）；pin_count 归零后同样把帧交还替换器。真正落盘发生在该帧被选为 victim 或显式 `FlushPage` 时：`FlushFrameLocked` 先按 page 的 LSN 把日志刷盘（WAL），再 `WritePage`，最后 `SetDirty(false)` 并把 `rec_lsn_` 清成 `INVALID_LSN`。

漏掉一次 Unpin，pin_count 永不回零，该帧永远进不了可淘汰集合；次数一多，8 个帧全部被钉死，新的 `FetchPage` 只能抛 `NJUDB_NO_FREE_FRAME`——多线程测试里表现为反复捕获异常、sleep 重试，严重时直接卡住。脏位传错的后果不对称：写操作传 false，改动不会写回，页被淘汰后数据就丢了（写后读的 `memcmp` 会失败）；读操作传 true 则不必要地多一次写回，I/O 放大但结果正确。本实现里脏位是粘性的，一次 false 的 Unpin 不会清掉已置上的脏位，所以「读路径把脏位清掉」的风险不存在。

### 问题二：替换器如何保证只淘汰允许淘汰的帧？请给出并发或边界场景，说明状态在哪一步更新。

保证来自两道闸门。第一道在缓冲池：帧只有在 pin_count 降到 0 时才会交给替换器，位置就是 `UnpinPage` 里的 `if (!frame.InUse()) replacer_->Unpin(frame_id)`。第二道在替换器内部：每个节点带一个 `evictable` 标志，`Victim` 只在该标志为 true 的节点里挑，因此链表里即使存在被 pin 住的帧也不会被选中。

并发场景取多线程测试：8 个帧、10 个线程同时 `FetchPage` 不同页。线程 A 拿到某帧时 pin_count 为 1、evictable 为 false；线程 B 此时需要新帧，`GetAvailableFrame` 先看 `free_list_`（空），再调 `Victim`——A 的帧因标志为 false 被跳过，B 只能选别的帧；若此刻 8 个帧都在使用中，`Victim` 返回 false，`FetchPage` 抛 `NO_FREE_FRAME`，B 稍后重试。状态更新点很明确：pin 时在 `FetchPage` 里同时更新引用计数与替换器标志；unpin 时在 `UnpinPage` 里先减引用计数，归零后再更新替换器。

另一个边界是 `DeletePage`：帧还给 `free_list_` 前必须调用 `replacer_->Remove` 把它从替换器中彻底摘掉。若只标成不可淘汰而留在链表里，它会同时出现在两处、可能被重复分配；若沿用「用 `Pin` 顶替 `Remove`」，LRU-K 还会把旧页面的访问历史带给下一次装入的新页面，导致淘汰顺序错乱。

## 五、对框架与实验的建议

- 头文件注释与文档、测试不一致：`lru_replacer.h` 中 `Pin` 第 2 步写的是「若帧不在哈希表中直接返回」，但文档与 `ReplacerTest` 都要求新帧先登记；照注释实现会在 `RandomlyPinUnpin` 与 `VictimOrder` 两段失败。建议统一以文档和测试为准并修订注释。
- `PageGuard` 只有 pin/unpin，没有页级读写锁。文档把 pin_count 与 latch 并列讲解，但 `page_guard.h` 中没有 latch，并发写保护实际只靠引用计数；多线程测试是靠外部串行化与 `NO_FREE_FRAME` 重试才跑通的。建议补页锁，或在文档中说明当前模型。
- 职责边界不清晰：t3 的函数同时牵扯 2PL 加锁、WAL 日志与事务写集合，三者分属 Lab05/06；只按 Lab01 要求实现 CRUD 会连带让 Lab05 的 MVCC 用例失败，建议在文档中标注这些必需钩子。
- `BufferPoolManager` 默认 `replacer_lru_k` 为 0，而配置默认启用 `LRUKReplacer`，K=0 会使访问历史永远为空，建议构造时做一次合法性校验。
