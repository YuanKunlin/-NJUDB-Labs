## 二、实现思路

### 1. 嵌套循环内连接（t1）

t1 与 Lab02 附加题 f1 指向同一组函数（`InitInnerJoin/NextInnerJoin/IsEndInnerJoin`），代码在上一实验已完成，本次主要是验证：外层扫左表、内层扫右表，每条候选用 `Record(out_schema_, *left_rec_, *right)` 拼成连接记录后先 `right_->Next()` 再 `ConditionExpr::Eval`，内层耗尽则 `left_->Next()` + `right_->Init()` 回卷。`out_schema_` 由基类按「左 schema ++ 右 schema」拼好，拼接顺序必须与之一致；`left_rec_` 存拷贝，避免右表推进影响当前左行；条件为空时 `std::all_of` 对空区间返回 true，天然支持笛卡尔积。`Init` 取完第一行左记录后立刻调用一次 `NextInnerJoin()`——`IsEnd()` 只认 `record_ == nullptr` 哨兵，`Init` 不算出第一条就无法区分"还没算"和"已结束"。复杂度 O(|L|×|R|)。

### 2. 循环嵌套左外连接（t2）

与内连接的差别只有一处：左记录在右表中无匹配时补一条右表全 NULL 的记录。难点是这个判断**必须跨 `Next` 调用保存**——一条左记录可能先输出若干匹配行，扫完才决定是否补 NULL。头文件预留的成员 `need_gen_null_` 正好表示"当前左行还没匹配过"：

```c++
if (ConditionExpr::Eval(conditions_, *joined)) {
  need_gen_null_ = false;                    // 已有匹配
  record_        = std::move(joined);
  return;
}
Record null_right(right_->GetOutSchema());   // 全 NULL 右记录，nullmap 全置 1
null_row = std::make_unique<Record>(out_schema_.get(), *left_rec_, null_right);
left_->Next();                               // 返回 NULL 行之前先推进左记录！
need_gen_null_ = true;
```

两个细节：**返回 NULL 行之前必须先推进左记录**，否则下次 `Next` 进来时左指针还停在原行、标志刚被重置，会再补一次同样的 NULL 行；**NULL 扩展行不再参与条件求值**，本引擎 `NULL == NULL` 返回 true，把 NULL 行丢回 `ConditionExpr::Eval` 会让 `s_i_id = i_im_id` 把空值判成相等、凭空多出结果。

### 3. 聚合算子（t3）

框架把聚合拆成"累加器 + 分组表"，四个钩子分别是：

- **恒等元**：COUNT 系列为 0，SUM/AVG/MAX/MIN 为 NULL。SUM 用 NULL 而非 0，才能区分"没有任何输入"与"输入的和为 0"（文档要求空输入时 `select sum(x)` 输出 0 行）。
- **单行贡献**：COUNT(\*) 恒为 1；COUNT(col) 按 col 是否 NULL 取 0/1；SUM/AVG/MAX/MIN 取列值；AVG 另把 `avg_count_map_[i]` 记 0/1。
- **合并**：COUNT/SUM 走虚函数 `Value::operator+=`，MAX/MIN 比较后接管 `shared_ptr`，AVG 同时合并计数。不能写 `*values_[i] = *rhs`——`Value` 的赋值运算符非虚，会**对象切片**丢掉 `IntValue::value_` 这类派生类字段。
- **终结**：只处理 AVG，`*values_[i] /= count`。框架为各类型预置了 `operator/=`（注释写明"用于聚合中的平均值计算"），int 走整除、float 走浮点除，正好复现 gold 的 `avg(s_quantity)=5`、`avg(i_price)=5.693364`。

执行器用 `unordered_map<Record, AggregateValue>` 做**单遍哈希分组**而非排序分组，所有键都用同一个 `group_schema_.get()` 构造（`Record` 的 `operator==` 比较 schema 指针，指针一致才能做 map key）：

```c++
while (!child_->IsEnd()) {
  auto record = child_->GetRecord();
  auto [iter, inserted] = group_map_.try_emplace(MakeGroupKey(group_schema_.get(), *record),
                                                 agg_schema_.get(), *record);
  if (!inserted) iter->second.CombineWith(AggregateValue(agg_schema_.get(), *record));
  child_->Next();
}
```

两个易错点：**源列定位不能用 `GetRTFieldIndex`**，因为 COUNT(col) 的字段类型被 planner 改成 INT、`field_` 已与子记录源列不一致，要按 `(table_id, field_name)` 用 `GetFieldIndex`；**空输入有特殊语义**，无 GROUP BY 且子算子为空时仍"有一个分组"，构造恒等元并终结后，有非 NULL 结果才输出一行（`count(*)` 为 0 → 输出 0），全 NULL 则 0 行。HAVING 不在聚合内部：planner 会把 HAVING 的聚合列补进 `agg_fields` 再在聚合之上包 `FilterPlan`，聚合只需输出 `group ++ agg` 并保留 `is_agg_/agg_type_/field_` 元信息。

### 4. 哈希连接（f1）

`OptimizeHashJoin` 先要求至少一个等值条件（否则退化为嵌套循环），把等值条件的左右列收集成两侧 key schema，并**把这些等值条件从 `conds_` 中删除**——执行器看到的 `conditions_` 只剩非等值残差谓词（如 `s_ytd > i_price`）。执行器分两阶段：build 右表（`hash_table_` 按哈希存**右记录副本**，因为右算子还会继续 `Next()`；同时把哈希插入布隆过滤器），probe 左表（算哈希 → 布隆判"肯定不在"则跳过 → 查桶 → 候选过一遍 `CheckJoinCondition` 检查残差谓词 → 拼接输出）。多列键按 key schema 顺序做 `hash_combine`，保证两侧相同键值哈希相同。外连接复用 `current_left_has_match_`，候选扫完未匹配则补 NULL 行，同样"先推进左记录再返回"，probe 侧必须是保留侧（左表）。连接键含 NULL 的记录不入表也不探测——本引擎 `NULL == NULL` 为 true，这条标准 SQL 语义必须显式实现。复杂度 O(|L|+|R|)。

### 5. 排序合并连接（f2）

与 f1 不同，f2 **不自己排序**：`OptimizeSortMergeJoin` 已把两侧子算子包成 `SortPlan`（等值两侧升序；`>`/`>=` 左降右升；`<`/`<=` 左升右降，见 `GetSortMergeOrdering`），并把操作符记到 `join_op_`；执行器构造时 `conditions_` 传空，连接语义完全由 `join_op_ + 两个 key schema` 表达。实现共用一套状态：当前左记录 + 右记录缓冲 + 缓冲游标。**等值连接**：右表升序，跳过右键更小的、遇到更大的就停、相等的收进缓冲，输出"左记录 × 缓冲"；左键没变就复用缓冲，所以右表只扫一遍。**非等值连接**：排序方向保证"满足条件的右记录永远是右表的一个前缀"，第一行左记录（边界）匹配最多，左键往更难满足的方向移动时只需从**尾部**弹掉不再满足的记录，右表一次都不用回卷：

```c++
while (!right_buffer_.empty() && !EvaluateJoinCondition(*left_rec_, *right_buffer_.back())) {
  right_buffer_.pop_back();
}
```

`>`/`>=` 与 `<`/`<=` 完全对称，所以"大于族"直接复用"小于族"；内外连接共用一套代码，`join_type_` 决定是否补 NULL 行。复杂度：等值 O(|L|+|R|)，非等值右表虽只扫一遍，但每条左记录要遍历匹配前缀，最坏仍 O(|L|×|R|)。

### 6. 三种连接对比

| 连接方式 | 适用谓词 | 输入顺序要求 | 内存 | 时间复杂度 |
| --- | --- | --- | --- | --- |
| 嵌套循环 | 任意（含 OR、多列非等值） | 无 | O(1) | O(L·R) |
| 哈希连接 | 至少一个等值 | 无 | O(R) 哈希表（+布隆） | O(L+R) |
| 排序合并 | 多列等值；单列非等值 | 必须有序（优化器插 Sort） | O(匹配前缀) 缓冲 | 等值 O(L+R)，非等值最坏 O(L·R) |

## 四、实验问题

### 问题一：左外连接中 executor 在哪些状态下继续扫描、返回匹配行或构造 NULL 行？如何保证只生成一次未匹配结果？

状态为 `left_rec_`（当前左记录拷贝）、`right_` 游标、`need_gen_null_`（当前左行是否尚未匹配）、`record_`（当前输出兼结束哨兵）。**继续扫描**：`Next` 维护两层循环，内层每拼一条候选就 `right_->Next()`（先推进再求值，不会重复看到同一候选），内层扫完则外层 `left_->Next()` + `right_->Init()` 回卷。**返回匹配行**：条件成立时置 `need_gen_null_ = false`，把拼接记录放进 `record_`。**构造 NULL 行**：内层扫完时若标志仍为 true，用 `Record(right_->GetOutSchema())` 造全 NULL 右记录拼成扩展行，**返回前先推进左记录**并刷新 `left_rec_`、`right_->Init()`。**只生成一次**靠两点：标志存成员（跨调用保持）、返回 NULL 行前就推进左记录；若标志是 `Next` 的局部变量，匹配过的左记录在输出完匹配行后会被再补一条 NULL（见问题四）。

### 问题二：聚合算子为每个分组保存了哪些中间状态？任选两个聚合函数说明更新与终结

每个分组保存一个 `AggregateValue`：`values_`（每个聚合列一个运行值：COUNT 的计数、SUM/AVG 的运行和、MAX/MIN 的极值）、`avg_count_map_`（AVG 列的非空计数，作为分母单独记录）、`summarized_`（终结幂等标志）。**COUNT(\*)**：恒等元 0，每条输入贡献 1（NULL 行也算，不看任何列），合并即整数相加；空输入结果为 0 且非 NULL，所以空表也输出一行 `COUNT(*) = 0`。**AVG(col)**：恒等元 NULL、计数 0；col 非 NULL 时贡献列值且计数 1，否则 NULL 且计数 0；合并时和、计数分别相加；终结时计数为 0 或和仍为 NULL 则结果 NULL，否则 `*values_[i] /= count`——聚合字段类型沿用源列类型，故 `avg(int列)` 整除（528/100 = 5）、`avg(float列)` 浮点除（5.693364）。空输入时 AVG 为 NULL；若整体聚合结果全为 NULL（如无输入的 `select sum(x)`），聚合输出 0 行，否则 1 行。

### 问题三：选两种连接方式，结合执行器接口说明输入顺序、内存、谓词类型的要求与选择策略

以**哈希连接**和**排序合并连接**为例（对照嵌套循环）：

- **输入顺序**：哈希连接无要求（build 扫右表、probe 扫左表各一遍）；排序合并**必须**两侧有序，且顺序由优化器保证——它把子算子包成 `SortPlan`（等值两侧升序，`>`/`>=` 左降右升，`<`/`<=` 左升右降），执行器不排序。
- **内存**：哈希连接需 O(|R|) 哈希表（外加布隆过滤器）；排序合并只为"当前左记录的匹配前缀"开缓冲，最坏 O(|R|) 但通常小得多。
- **谓词类型**：哈希连接要求至少一个等值条件（等值条件已被优化器删除，只剩列对；其余非等值条件作为残差由执行器二次过滤）；排序合并支持多列等值，非等值只支持单列。
- **选择策略**：等值连接且能接受 O(|R|) 内存时用哈希连接（一次扫描、无排序）；输入本来有序（索引扫描提供顺序）或谓词为非等值时用排序合并；谓词含 OR、多列混合比较时只能嵌套循环。测试里三种方式对同一查询输出完全一致，说明切换策略不改变语义。

### 问题四：给出一个曾使 Join 或 Aggregate 失败的 SQL 或测试场景，说明错误输出如何帮助定位

实现 t2 时，若把"当前左记录是否匹配过"写成 `NextOuterJoin` 里的局部变量 `bool has_match = false`，`03_join` 就会失败。本次实验特意改回局部变量重跑评测：`Passed [3/5]`，`03_join` 与 `04_aggregate` 同时失败，`03_join` 与 expected 的 diff 有 1045 行。错误输出的特征很清楚：差异**只出现在第 7 条查询之后**（前 6 条是笛卡尔积与内连接，不涉及 NULL 行逻辑）；多出来的行都是"左列正常、右列全空"的形态；行数**整体膨胀**（`100 → 200`、`5050 → 5150`、`157 → 200`、`7592 → 7692`，多出的行数正好是匹配过的左记录数）；`04_aggregate` 也跟着失败，因为其中 5 条聚合查询的子计划正是 `stock outer join item`，多出的 NULL 行直接改变统计值。这些线索排除了"连接条件写错"（那会缺行或错行，而不是每条匹配行后多一行全 NULL）和"扫描顺序问题"（差异位置应随机），把问题锁定在**判定状态没有跨 `Next` 调用保留**；改成成员 `need_gen_null_` 并在返回 NULL 行前先推进左记录后，两个用例同时恢复逐字节一致。这也说明聚合的正确性依赖子算子输出的行集合，join 多补的行不会被聚合"消化"。

## 五、对框架与实验的建议

- 三种连接接口风格不统一：哈希用"删等值条件 + 传列对"、排序合并用"传 `join_op_` + 列对且 `conditions_` 为空"、嵌套循环直接吃完整条件，建议统一成"条件 + 键模式"的显式结构。
- 哈希连接按哈希值分桶而不比较键值本身，理论上碰撞会误连（int 键在 libstdc++ 下是恒等映射，实际不发生）；多列键、字符串键建议增加键值校验。
- 优化器选择哈希连接时不检查左右键类型，`int = float` 会因两侧哈希不同而漏匹配；建议加类型兼容判断或在执行器内对齐类型后算哈希。
- 布隆过滤器大小（8192 bit、3 个哈希函数）在构造函数里硬编码，建议做成可配置项或按 build 侧行数估算。
- 测试用例都带 `ORDER BY` 且覆盖全部选择列，掩盖了三种连接的输出顺序差异；表也只有 100 行，复杂度差异体现不出来，建议补一组无 `ORDER BY` 的用例和几千到几万行、带重复键的数据。
