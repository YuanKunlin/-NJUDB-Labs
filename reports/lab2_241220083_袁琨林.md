## 二、实现思路

### 1. 扫描与过滤：两种「推进」语义

`SeqScanExecutor` 是叶子算子，用 `TableHandle::GetFirstRID/GetNextRID` 遍历 RID，再由 `LoadCurrentVisibleRecord` 把「物理存在但不可见」的记录跳过（并发删除、MVCC 不可见都会抛 `RECORD_MISS`）。它的结束条件是 `rid_ == INVALID_RID` 而**不能**是 `record_ == nullptr`，因为上述辅助函数内部用 `while (!IsEnd())` 驱动，若 `IsEnd` 依赖 `record_` 就形成循环依赖。

`FilterExecutor` 是流水线算子，`Next()` 里循环向下要行，直到谓词成立：

```c++
while (!child_->IsEnd()) {
  auto record = child_->GetRecord();          // 拷贝，child 会复用 record_
  if (filter_(*record)) { record_ = std::move(record); return; }
  child_->Next();
}
record_ = nullptr;
```

关键点是 **`Init()` 只评估 child 当前行、不推进，`Next()` 先推进再评估**；若 `Init` 里也调 `Next`，第一行会被跳过。谓词由 `ConditionVec` 编译成闭包，执行器不解析 WHERE。

### 2. 投影与分页：一对一变换

`ProjectionExecutor` 用 `Record(out_schema_, *child_record)` 按字段定义（表 id + 名字 + 类型 + 长度）从整行中挑出需要列重排，NULL 位一并搬运；因此 `select gpa, name` 这种换序、以及排序键不在输出列的场景都成立。注意该构造函数会把新记录 RID 置为 `INVALID_RID`，所以需要 RID 的算子（Update/Delete）必须直接接在扫描/过滤下方。

`LimitExecutor` 维护已输出行数 `count_`：`Init` 里 `count_ = 0` 并在 `limit > 0` 时定位第一行；`Next` 先自增，达到上限即置空结束，且**不再多拉一次 child**；`limit` 大于实际行数时靠 child 耗尽提前结束；`limit 0` 不推进 child。

### 3. 排序：内存排序与外部归并

`SortExecutor` 是阻塞算子，`Init` 必须物化全部输入。`max_rec_num_ = 64MB / 行宽`：装得下就 `std::sort` 一次；装不下则分块排序、逐块写入 run 文件，再做多路归并。

run 文件的记录格式为 `[page_id][slot_id][nullmap][data]`，写读两端严格对称。归并每轮把最多 `SORT_WAY_NUM = 10` 个 run 用小根堆合成下一组的一个文件，组号递增，每轮结束删除上一组文件；最终结果由 `LoadMergeResult()` 读回 `sort_buffer_`，因此 `Next/IsEnd` 与内存排序共用同一套游标逻辑。

```c++
auto cmp = [this](const SortHeapNode &a, const SortHeapNode &b) {
  return Compare(*b.GetRecord(), *a.GetRecord());   // 反转成小根堆
};
```

踩过的一个坑：归并时读取每条 run 使用的是 `LoadNextRecord(max_rec_num_)`，但 `max_rec_num_` 是**单块缓冲容量**而非**文件长度**，第二轮归并后 run 已远大于它，导致每个 run 只读出 `max_rec_num_` 条，最终结果只剩 1/10。改为用 EOF 判断、上界放开后正确。

### 4. 写算子：动作型算子的统一骨架

Insert / Delete / Update 都是 DML 动作型算子：`Init` 完成全部动作并生成一行计数（`inserted` / `deleted` / `updated`），`Next` 只置结束标志，`IsEnd` 返回该标志，因此 `Init` 需要复位 `is_end_` 以支持重复执行。

三者的差异在数据来源与维护顺序：

- **Insert**：值已在 `inserts_` 中，直接 `TableHandle::InsertRecord` 拿到 RID，**先 `SetRID` 再插索引**（索引项存的是记录自带 RID）；MVCC 事务走 `MVCCWriteCoordinator`，2PL 的加锁、WAL、事务写集合由 Lab01 的 `TableHandle` 内部完成，执行器不重复做。
- **Delete**：从 child 拉行取 `record->GetRID()`，先删索引项（索引键需要完整元组）再删表行；边删边扫是安全的，因为扫描游标按「当前槽号 + 1」前进，不会回头。
- **Update**：**先把整批 old/new 记录物化，再统一应用**。边扫边改会引发 Halloween 问题（例如自增列被重复更新）。新记录由 `GetValues()` 取出各列、替换被更新字段、再以原 RID 重新构造，从而复用框架的类型转换、字符串越界检查与 nullmap 重建。

### 5. 嵌套循环内连接（f1）

```c++
while (!left_->IsEnd()) {
  while (!right_->IsEnd()) {
    auto joined = std::make_unique<Record>(out_schema_.get(), *left_rec_, *right_->GetRecord());
    right_->Next();
    if (ConditionExpr::Eval(conditions_, *joined)) { record_ = std::move(joined); return; }
  }
  left_->Next();
  if (left_->IsEnd()) break;
  left_rec_ = left_->GetRecord();
  right_->Init();           // 右表回卷
}
```

`out_schema_` 在 `JoinExecutor` 构造时由左右 schema 拼接而成；`left_rec_` 必须是拷贝，右表反复推进不影响它。复杂度为 O(N×M×谓词代价)，但这是 f1 指定的内连接实现，也是理解连接算子代价模型最直观的起点。

## 四、实验问题

### 问题一：选一个由两个以上算子组成的计划，说明 `Init`、`Next`、`IsEnd` 在父子算子间的调用顺序

取 `select name from dbcourse where gpa > 4 order by id limit 5`，计划树为 `Projection(Limit(Sort(Filter(Scan))))`。

`Execute` 只驱动根节点，递归体现在调用栈中：

```
Init(Projection) → Projection::Init → Limit::Init → Sort::Init → Filter::Init → Scan::Init
                     Filter::Init 内部循环 Scan::Next 直到谓词成立
                     Sort::Init 循环 Filter::Next 直到结束，排序后定位第 0 行
                     Limit::Init 取 Sort 第 0 行（count_ = 0）
                     Projection::Init 投影 Limit 当前行
循环体：IsEnd(Projection) → GetRecord(Projection) → 发送 → Next(Projection)
        Projection::Next → Limit::Next（count_ < limit，不结束）
        Limit::Next   → Sort::Next（游标 +1）
```

`Init` 阶段的顺序是自上而下、但真正的工作是自下而上完成的：每个算子在 `Init` 里先 `child_->Init()`，然后完成自己的定位。循环阶段则是「`IsEnd` 只读状态、`GetRecord` 取拷贝、`Next` 负责推进」。三个接口的分工不能混：`IsEnd` 是 `const`，不允许拉数据；`Next` 不返回值；`GetRecord` 返回的是当前行的拷贝。

### 问题二：过滤与投影各自的输入/输出 schema；顺序或字段索引错误会怎样

以 `select name from dbcourse where gpa > 4` 为例：

- `Filter` 的输入 schema 是**整表 schema**（含 `gpa`），输出 schema 与输入完全相同——过滤只改变行数，不改变形状。
- `Projection` 的输入是整表 schema，输出是**只含 `name` 一列的新 schema**。

所以谓词使用的 schema 比最终输出宽：`gpa` 并不在输出列里，但过滤阶段必须可见。若把两者顺序颠倒（先投影再过滤），`Filter` 拿到的记录里没有 `gpa`，`ConditionExpr::Eval` 中 `GetRTFieldIndex` 找不到字段会触发 `NJUDB_ASSERT("Invalid field")` 直接中止；即便不做断言，也只能取到空值，表现为**结果集为空或行数明显偏少**。

如果投影实现按「列位置」而不是「字段定义」匹配，`select gpa, name` 这类换序投影就会把两列数据写反，现象是查询能跑通但**值和列名错位**，与 `expected` 逐行 diff 会立刻暴露。框架的 `Record(schema, other)` 按字段名、类型、长度匹配，正是为了避免这类错误。

### 问题三：以 UPDATE 为例，说明表达式结果如何变成记录修改、如何维护返回行数与一致性；指出一个必须处理的边界

`updates_` 是 `(RTField, ValueSptr)` 列表，值在计划阶段已求值。执行器先遍历 child（`Filter(Scan)`，RID 完整）把整批 old/new 物化：

```c++
auto old_record = child_->GetRecord();
auto values     = old_record->GetValues();
for (auto &[field, value] : updates_) values[old_record->GetSchema()->GetRTFieldIndex(field)] = value;
auto new_record = std::make_unique<Record>(old_record->GetSchema(), values, old_record->GetRID());
```

随后统一应用：先 `IndexHandle::UpdateRecord(old, new)`（删旧键、插新键），再 `TableHandle::UpdateRecord(rid, new, txn)`（2PL 的加锁、WAL 与事务写集合在内部完成）。返回行数是实际应用的记录条数，`where` 命中 0 行时输出 `updated = 0`。

**必须处理的边界**：`where` 条件涉及的列正好是被更新的列（如 `update t set score = score + 1 where score > 60`）。若边扫边改，某行自增后仍满足条件会被二次更新，结果偏大。本实现通过「先物化全部 old/new、扫描结束后再应用」避免了这个 Halloween 问题；同时这也让 lab04 的批量唯一性校验成为可能——只有看到整批结果才能判断批内是否冲突。

## 五、对框架与实验的建议

- `config.h` 缺少 `<cstdint>`，gold 模式下测试不到，切源码编译即报错，建议补上。
- `ORDER BY` 的降序语法是 `ORDER BY desc <列>`（方向在列前），与 SQL 标准的 `order by <列> desc` 不同，标准写法会直接语法错误；建议至少兼容标准写法或在文档中显著说明。
- `SortHeapNode::LoadNextRecord(max_rec_num)` 的参数名容易被理解为「文件内记录数」，实际是缓冲容量，第一轮之后就不再适用，容易写出「只读出 1/10」的隐蔽 bug，建议改名为 `max_read` 或改用 EOF 判断。
- 相等键的先后顺序未定义，但测试用例中存在 `update ... set id = -1` 制造出的重复键，`std::sort` 与归并实现的 tie 顺序不同会造成逐行 diff 不一致；建议用例避免依赖相等键顺序，或在比较器中给出确定的 tie-break。
- Insert 的执行器里同时存在 Lab02 的插入与 Lab04 的唯一性校验注释，职责边界需要读者自行判断，建议在文档中标注哪些属于后续实验。
- 客户端逐条发送 `insert` 时吞吐较低（1000 条约 1~2 分钟，Debug 构建），批量插入时影响调试效率。
